# AI应用广场需求说明

版本：0.1 · 评审草稿 · 2026-10-10

文档任务：[Docs #3](https://github.com/Dylan5237/ai-app-plaza/issues/3)

适用读者：产品、研发、测试及应用作者

本文整理已确认的产品方向与现有原型，不代表需求已经冻结或功能已经实现。“已确认方向”来自用户要求；“建议规则”供本轮评审；“待决策”不能在开发时自行作为已确认结论。当前原型的真实覆盖范围见[能力边界说明](capability-boundaries.md)。

## 1. 产品目标

让用户从“我想完成什么”出发，找到团队已有的 AI 能力，并尽快开始使用；让成果作者通过自己的 Agent 整理和分享项目，降低重复建设与成果复用的成本。

应用广场负责发现、说明和连接应用。入驻应用的源码、版本与主要业务资料来自 GitLab；作者的 Agent 负责结合项目上下文整理资料、发起并跟踪已授权的发布操作，使用者的 Agent 负责按提示词完成接入。发布操作由 Agent 直接调用还是经广场服务执行，见 Q4。

### 已确认方向

- 以能力需求组织入口，不要求使用者先理解 Skill、MCP、插件、脚本等形态。
- 同一个用户既可以使用应用，也可以分享自己的 AI 应用；产品流程覆盖这两种使用场景。
- 作者通过 Agent 提供与维护资料，广场提供只读预览和结果反馈，不要求作者逐字段手填。
- 平台应用跳转到平台链接；其它应用统一通过“接入我的Agent”提供可复制的提示词。
- 标签由作者自定义，用户可根据标签筛选。
- 采用通用的应用描述与接入规则，不围绕现有 17 个示例项目做专用设计。
- 仅维护桌面网页版，依据用户明确要求“不用维护移动版的原型，只要网页版的”；界面延续已确认原型，不在本文重新定义视觉样式。

### 预期价值

使用者能判断“是否适合、需要准备什么、怎样开始”；作者能通过一次完整的 Agent 协作发布可理解、可使用的成果。后续可观察查找到应用的比例、进入使用入口的比例及发布收录成功率，具体指标口径与目标值待实际业务基线建立后确定。

## 2. 用户及协作方

| 对象 | 目标 | 在流程中的责任 |
| --- | --- | --- |
| 使用者 | 找到适合当前任务的能力 | 描述目标、筛选与判断适用性，打开平台或将接入提示词交给自己的 Agent |
| 作者 | 分享和更新自己的 AI 应用 | 向 Agent 表达发布意图、审阅预览、确认发布范围，维护应用资料 |
| 作者的 Agent | 将项目上下文转为可分享的应用 | 读取项目、生成资料、检查缺项，发起并跟踪作者授权的发布操作，报告实际结果；直接写入与服务代办边界见 Q4 |
| 使用者的 Agent | 将应用接入用户环境 | 根据提示词核对环境、取得所需授权、安装或配置、验证并说明结果 |
| 应用广场 | 帮助发现和复用 | 汇聚可见资料、提供搜索筛选与使用入口，展示发布预览和可信的处理结果 |
| GitLab | 保存项目与版本资料 | 提供仓库、文档、版本及访问权限所依据的信息 |

使用者与作者是两种业务场景，不据此要求两套账号。是否需要单独开通发布权限，见待决策 Q1。

## 3. 范围与职责边界

首期范围包括：能力发现、作者标签筛选、应用详情、平台访问、Agent 接入提示词，以及“分享我的AI应用”的资料生成、预览、确认、结果与修复流程。收藏为现有原型能力，建议保留；其账号同步规则尚未确定。

以下能力不属于本轮默认范围：托管所有应用的计算服务、在广场内运行用户的 Agent、代替平台应用处理具体业务、建立通用安装/部署执行器、移动端适配，以及未被要求的评论、评分、排行榜、计费与复杂审批体系。

需要本地部署的工具可以由使用者的 Agent 从公司提供的合法分发地址下载和部署。广场提供接入说明与来源信息，部署执行、凭据获取和环境变更发生在用户授权的环境中。

GitLab 是应用资料与版本的主要来源。广场可保存收藏、发布草稿、收录与同步结果等自身业务状态，不能据此形成另一套与仓库无关联的应用资料。

## 4. 使用应用

### 4.1 能力发现

主路径：描述所需能力 → 查看匹配应用 → 按标签缩小范围 → 查看详情 → 开始使用。

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| U01 | 以工作目标查找应用 | 用户可用自然语言描述任务、输入材料或预期产出；不必知道项目名称或技术形态 |
| U02 | 提供可比较的应用信息 | 列表展示项目名称、简要能力说明、作者标签、作者、版本、创建时间和更新时间 |
| U03 | 支持作者标签筛选 | 展示作者维护的标签；支持选择、取消与清空条件，并能与能力查询组合 |
| U04 | 保留通用浏览方式 | 未输入需求时仍可浏览应用；无结果时说明当前未找到匹配项，允许调整描述或标签 |
| U05 | 支持收藏（建议保留，待确认） | 承接现有原型，便于再次访问；收藏不是应用可用性或权限证明 |

建议规则：多个标签按“同时包含”筛选，与需求查询结果取交集；清空标签保留当前查询。该规则与原型一致，仍需评审确认。标签同义词、大小写与重名处理也属于 Q2。

自然语言输入不等于已经确定使用语义模型。搜索应帮助找到相关能力；具体检索实现、排序因素和可接受效果需另行评估。没有匹配结果不能表述为团队中绝对不存在这种能力。

### 4.2 判断适用性

应用详情应回答：适用于什么任务、需要什么输入和环境、能获得什么结果、有什么限制，以及从哪里开始使用。

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| U06 | 信息足以支持使用判断 | 展示能力与适用场景、输入、产出、前置条件、示例任务及必要的使用边界 |
| U07 | 使用说明容易获得 | 用户能直接阅读开始使用所需的步骤与说明；项目仓库、文档和版本信息可查；具体展示沿用原型 |
| U08 | 只提供适用的使用入口 | 平台入口指向作者登记的应用链接；其它入口提供 Agent 接入提示词 |
| U09 | 状态表达真实 | 区分资料完整、已收录、入口可访问、实际接入成功；不把这些状态合并为一个“已可用” |

作者没有提供的信息应指出缺项或回到作者 Agent 补齐，不能由广场编造。应用入口失效、版本资料缺失等情况应明确告知，并保留可追溯的仓库或作者信息。

### 4.3 平台应用

用户点击平台按钮后，跳转至登记的平台链接。平台自身负责登录、授权和业务处理；广场是否接入统一登录属于 Q1，不能默认已经具备。

平台链接应对应所展示的应用。打开页面不代表该平台的业务执行成功，广场也不能据此替应用作效果承诺。

### 4.4 接入我的Agent

用户打开接入提示词 → 复制 → 在自己的 Agent 中运行 → Agent 说明接入结果和首次使用方式。

接入提示词应使 Agent 能获得以下信息：

1. 目标应用、对应版本、可信的仓库或分发来源。
2. 需要的宿主、系统环境、依赖及权限，以及如何发现缺项。
3. 接入操作和完成后可执行的最小验证任务。
4. 已存在相同版本或配置时的处理方式，及失败后的恢复指引。

提示词不包含明文凭据；所需授权通过用户认可的渠道取得。涉及环境修改时，遵守用户当前 Agent 的权限机制。

广场提供提示词，不把“已复制”显示为“接入成功”。首次范围不要求直接控制用户的 Agent；是否回传接入结果尚未确定，也不作为发布收录成功的条件。

## 5. 分享我的AI应用

主路径：复制发布提示词 → 在有项目上下文的 Agent 中运行 → 查看发布预览 → 确认 → 查看结果。作者通过自然语言调整草稿，无须在广场手工填写项目资料。

| 阶段 | 作者与 Agent 的行为 | 广场应提供的结果 |
| --- | --- | --- |
| 发起 | 作者复制发布提示词交给自己的 Agent | 清楚说明要整理的资料、发布目标和需要返回的结果 |
| 整理 | Agent 读取源码、README、版本与项目说明，识别适用场景及入口 | 接收可预览的资料；不完整或互相冲突的信息有明确反馈 |
| 澄清 | 对无法从项目证据确定的关键项，Agent 向作者提问 | 保留缺项，避免用猜测填成事实 |
| 草稿回传 | Agent 按统一接入方式提交资料，关联作者、目标应用/仓库和本次发布 | 作者能进入对应草稿的预览，不用粘贴结构化数据或重新手填；关联信息不足时明确指出缺项 |
| 预览 | 作者查看名称、能力、标签、说明、版本、入口、目标仓库与发布范围 | 只读预览；既能判断应用呈现效果，也能看清即将对外分享的内容 |
| 调整 | 作者向 Agent 用自然语言提出修改，Agent 更新草稿 | 返回新的预览，不要求作者改结构化字段 |
| 确认 | 作者确认当前草稿及发布范围 | 确认与所见内容对应；确认后发生实质修改时需要重新预览确认 |
| 执行与反馈 | Agent 或获授权的服务执行相应操作 | 分别展示源码、版本与广场收录的结果；失败时说明停在哪一步、下一步由谁处理 |

“确认与预览一致”及“仅重试失败步骤”是依据原型提出的建议规则，需在评审中确认；真实写入职责、是否存在组织审核见 Q4。

草稿从外部 Agent 返回广场的业务交接是完整流程的必要环节。提交结果应能让作者找到对应预览，并避免将不同作者或不同应用的草稿混用；回传失败时应保留可继续处理的资料。采用何种接入协议、如何确认作者身份与关联本次发布，见 Q4。现有原型的浏览器模拟流程尚未实现该交接。

### 作者标签

标签由作者自定义、由 Agent 根据作者表达生成或修改。AI 可以建议标签，作者可以在预览中确认或要求调整；不强制作者从预置技术形态分类中选一个。

标签应帮助使用者识别能力、用途或业务场景，不应包含凭据或不宜分享的信息。广场如何提示重复和近义标签、是否保留原始拼写，见 Q2。

### 发布预览需要表达的信息

预览既包含应用将如何被发现和使用，也包含目标仓库、版本、分享范围及拟上传文件摘要。仓库地址、版本等由 Agent 从上下文或作者自然语言中获取，不能用“作者不手填”代替必要的目标确认。

若资料涉及敏感文件或超出作者权限，应在执行前说明并让作者调整。允许分享给谁尚未定案，不能将私有仓库的收录默认理解为对所有访问广场的人公开。

### 发布结果与异常

| 情况 | 应给出的反馈 | 后续处理建议 |
| --- | --- | --- |
| 资料不完整或缺少入口 | 尚不满足收录条件，指出缺项 | 作者将补充提示词交给 Agent；更新后重新预览 |
| 仓库或发布权限不足 | 哪一步未执行、需要什么权限 | 通过正常授权渠道处理，不要求粘贴密码或令牌到广场 |
| 源码未上传成功 | 未上传成功，后续阶段不宣称完成 | 修复目标或上传问题后继续 |
| 源码已上传、版本未发布 | 保留已完成的上传结果 | 修复版本阶段，避免重复创建相同成果 |
| 仓库与版本已有结果、收录失败 | 明确已完成与失败的部分 | 提供针对收录的修复提示词；优先只重试失败部分 |
| 广场已收录 | 显示可访问的广场条目及对应版本 | 使用者仍需打开平台或在自己的 Agent 中完成接入 |
| 结果暂时无法确认 | 显示待确认或处理中 | 查询实际结果后再更新，不能用超时推断成功或失败 |

以上结果必须来自真实执行或同步证据；前端进度动画、点击确认及复制提示词都不构成成功证据。首次登记与后续更新如何复用同一应用、版本如何替换，见 Q3。

## 6. 应用需要具备的业务资料

以下是满足现有产品流程的最小信息类别，不是已经冻结的文件格式或 API。作者的 Agent 负责从项目中整理，无法确定时只询问必要缺项。

| 信息类别 | 使用目的 | 来源原则 |
| --- | --- | --- |
| 应用标识与项目名称 | 稳定识别同一成果，展示真实项目名称 | 与 GitLab 项目建立明确关联；标识策略待定 |
| 简介、能力与适用场景 | 支持查找和判断是否适合 | 作者维护的项目资料，由 Agent 提炼并经作者预览 |
| 作者与维护联系信息 | 识别来源、获得支持 | 使用可核验的项目身份；不把最近提交者自动等同于维护人 |
| 作者标签 | 表达能力特点并支持筛选 | 作者定义，Agent 辅助维护 |
| 版本 | 确认应用资料、入口和安装目标对应的版本 | 来自可定位的项目发布信息，口径见 Q3 |
| 创建时间、更新时间 | 帮助判断应用新旧及维护情况 | 来自约定的数据源；具体时间含义与更新触发条件见 Q3 |
| 输入、产出与前置条件 | 让用户知道如何准备和预期结果 | 项目文档与作者确认的信息 |
| 使用步骤、示例与限制 | 支持首次使用和合理预期 | 与当前展示版本一致的说明 |
| 使用入口 | 打开平台或让 Agent 完成接入 | 平台链接，或能取得固定版本说明的接入提示词及来源 |
| 仓库与文档引用 | 追溯资料、版本及使用说明 | 对应 GitLab 仓库和可访问文档 |
| 分享范围与发布结果 | 控制可见性、判断是否已收录 | 经授权确认的范围与真实处理结果 |

已确认 GitLab 为主要业务资料源；尚未确定资料究竟落在 README 的规范段落、独立描述文件还是二者结合。正式契约应便于 Agent 生成、广场校验和版本追溯，不要求作者手写结构化数据。

查询、标签和详情应使用一致的应用资料。当来源更新但广场尚未同步、来源不可访问或资料冲突时，应区分“已有资料”和“最新状态未确认”，不静默填补为正常。同步时机、失败重试与最长可接受延迟见 Q3。

## 7. 建议的业务验收场景

下表用于需求评审，尚未形成冻结的开发验收合同。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 用户描述工作目标，不知道项目名和形态 | 可以进入相关应用结果；结果帮助判断能力，不能只展示技术形态目录 |
| A02 | 作者通过 Agent 增加一个自定义标签并成功更新资料 | 广场展示该标签，用户可按该标签找到应用 |
| A03 | 用户组合需求与标签，得到空结果 | 明确提示无匹配，并可取消条件；不丢失原需求描述 |
| A04 | 用户查看应用详情 | 能找到准备材料、预期产出、使用步骤、入口、版本和必要限制 |
| A05 | 用户使用平台应用 | 按登记链接打开对应平台；未登录或无权限由明确的授权流程处理 |
| A06 | 用户接入 Skill、MCP 或需本地部署的应用 | 均由“接入我的Agent”获得对应版本的提示词；复制后不提前显示安装成功 |
| A07 | 作者在有项目上下文的 Agent 中发起分享 | Agent 资料回传后可进入关联正确作者、目标应用和本次发布的预览；不要求粘贴结构化数据或逐项填写表单；缺失信息由 Agent 澄清 |
| A08 | 作者要求改名称、描述或标签 | Agent 更新后返回新预览，发布内容与最后确认的内容一致 |
| A09 | 源码和版本成功、广场收录失败 | 保留已完成结果，反馈收录失败及修复路径；重试不重复创建应用 |
| A10 | 仓库有更新或暂时无法读取 | 按同步规则显示已同步版本及异常，不把旧内容误报为最新 |
| A11 | 应用或仓库不对当前用户开放 | 不因广场收录绕过权限，具体可见范围遵循已确认策略 |
| A12 | 新增一种未出现在现有 Mock 中的成果形态 | 能复用能力资料、标签和两类使用入口，无须新增一种形态目录 |

跨浏览器、页面交互和资源加载的检查沿用原型验证；搜索效果、发布延迟、并发容量等质量目标需结合真实环境补充，不能从 Mock 体验得出已达标结论。

## 8. 评审时需要决定的事项

| 编号 | 待决策事项 | 为什么需要决定 |
| --- | --- | --- |
| Q1 | 访问广场与分享应用的身份、权限及可见范围 | 决定谁能查看哪些项目资料、谁能发布，以及与 GitLab 和目标平台权限如何衔接 |
| Q2 | 标签的组合筛选、重名和近义词规则 | 原型使用多标签交集；需确认正式规则，同时保留作者自定义能力 |
| Q3 | 应用标识、版本/日期含义、资料载体与同步更新规则 | 保证更新不重复、资料与入口对应版本、日期表达准确，避免两套资料冲突 |
| Q4 | Agent 草稿回传、授权执行与审核边界 | 决定如何将外部 Agent 草稿交到对应作者和目标项目的预览、哪些写入由 Agent 或服务执行、如何取得授权、是否存在组织审核，以及如何恢复部分失败 |
| Q5 | 首期搜索效果与真实服务接入范围 | 区分自然语言输入、关键词匹配和语义理解；确定第一批环境及可验证的业务样例 |

这些决策不要求各项目作者补一套人工表格。平台级规则集中确认；每个项目的资料继续由作者的 Agent 按统一要求生成。

## 9. 现有材料的使用边界

当前原型包含 17 项完整 Mock，其中 6 项为平台演示、11 项提供 Agent 提示词。具体项目内容、版本、日期、示例域名、工作台结果和发布反馈均不构成真实交付或集成证据。

现有的本地关键词匹配、浏览器收藏、同源演示工作台以及模拟发布结果，用来帮助评审流程；它们不限制正式系统必须采用相同实现。正式需求应支持新增应用，不以已有项目数量、名称或 Mock 数据结构作为固定条件。

本草稿完成后，需要评审上述待决策项并形成需求基线；后续实现范围、接口和验收合同再按项目治理流程确认。
