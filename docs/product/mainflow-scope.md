# 首版主流程与边界

依据：用户于 2026-10-10 确认“先把发布收录、发现和使用这条主流程跑通”，并随后明确“先不做用户登录模块，就单纯一个所有人都能用的门户”。开发合同见 [Phase #7](https://github.com/Dylan5237/ai-app-plaza/issues/7)。这一最新指令覆盖架构提案中首期登录、账号绑定和用户收藏的安排。

## 本次实现

1. 作者复制发布提示词，让自己的 Agent 从项目中整理 schemaVersion 2 应用资料。每位作者须提供中文姓名和英文全名或完整拼音；资料缺任一姓名时，Agent 先询问作者，不从 GitLab 用户名、邮箱或 Git 配置推测。
2. 作者 Agent 按现有 GitLab 授权和项目发布流程准备固定 commit、版本 tag 与正式 Release。`projectVersion`、tag 和 Release 使用同一版本（支持 `1.2.3` / `v1.2.3` 与合法预发布号）；不要移动已有 tag，新 commit 使用新的匹配版本号。Agent 提交数字项目 ID、commit SHA、appKey、manifest 路径和 tag，广场读取并核验 `Release.commit.id`、`tag.commit.id` 与请求 SHA 一致，以及版本和共享资料。
3. 作者打开本次专属链接，预览将展示的内容后确认收录。收录失败时保留本次状态，恢复核验和收录，不重传源码。
4. 所有能访问门户的人都能搜索应用、组合作者标签、看详情，再打开平台链接或复制固定版本的 Agent 接入提示词。

直接 GitLab 发布由作者 Agent 按已有授权准备；固定群组的托管发布由广场服务器代办，见下文。广场不运行应用，不因收录开放仓库、软件包或目标平台权限。不做登录、账号、收藏、管理审批、应用运行托管、排行榜或移动端；本阶段不增加周期同步或高级检索。

## 负责人免 GitLab 配置发布

用户于 2026-10-13 明确要求负责人复制提示词即可上传，并确认在现有 `sky-efficiency-skills` 下建立 `AI-apps` 子群组。此需求按 [边界变更 #16](https://github.com/Dylan5237/ai-app-plaza/issues/16) 与 [Phase #17](https://github.com/Dylan5237/ai-app-plaza/issues/17) 扩展此前仅读 GitLab 的前提。

负责人在有当前项目文件和执行权限的 AI Harness 中运行提示词。AI 自动准备应用资料及必要源码，上传到广场；广场使用仅在服务器保存的群组授权，在固定私有群组内创建应用独立仓库、固定 commit、tag 和 Release，再生成原有私有预览。由负责人确认收录。负责人无需预建仓库或配置个人 GitLab 账号；缺失中文/英文姓名时，AI 仍先询问。

首次托管创建对能访问该内网门户的人开放，作者姓名是负责人确认的声明，不是员工身份认证。应用专属发布凭证在上传前由 AI 工具生成，安全保存在负责人本机；后续更新必须持有该凭证，并核验版本和广场修订，不能凭公开 appKey 修改他人应用。共享 GitLab 授权不进入客户端或公开资料。

上传只保存发布快照，不执行代码；新建仓库关闭 CI。文件路径、类型、数量及大小有明确限制，凭据和机器配置不得上传。网络结果不确定时复用同一操作和原文件对账恢复。预览未确认或收录失败不影响广场当前版本。既有直接 GitLab 发布方式继续可用，原有应用不自动迁移。

## 更新应用

依据 [Phase #14](https://github.com/Dylan5237/ai-app-plaza/issues/14)，更新沿用已有发布和接入流程，不增加管理后台或本地安装记录。

- 作者在应用详情选择“发布新版本”，复制已带入当前应用、仓库和版本的提示词。项目 Agent 准备资料与更高版本的 GitLab Release，提交后由作者预览版本变化与变更项，再确认更新。确认前或更新失败时原版本继续可用；成功后保留原应用编号、链接与创建时间。相同内容重复提交不增加版本；同版本改内容、版本倒退及过时预览覆盖均被拒绝。历史快照可更新为首个正式版本。
- 使用者仍选择“接入我的Agent”，复制安装／升级提示词。Agent 先核对广场当前已确认的版本及本地安装情况：未安装则安装，旧版按作者说明升级，已是目标版本则核验。配置、业务数据与本地修改须保留，需要时先备份；安装位置或升级依据不明确时询问使用者，不自动降级。执行后报告实际版本和验证结果。

这里的“最新版本”指广场已确认收录的版本。广场不跟踪用户的本地安装状态、不代替 Agent 执行升级，也不提供后台自动更新或通知。平台应用继续通过链接访问，由应用自身管理其部署版本。

## 应用详情的信息层次

依据用户于 2026-10-12 确认的方案 A（[Phase #11](https://github.com/Dylan5237/ai-app-plaza/issues/11)）：默认展示应用名称、版本、一句话简介、能力标签，以及主要用途、必要条件和简短使用步骤。中文作者姓名与创建、更新时间一起展示，英文姓名用于资料处理。

使用入口与可复制的示例任务放在右侧；示例逐条切换。接入提示词、完整应用资料和来源版本按需打开。概览复用作者已有资料，超出的用途、条件与限制仍可查看；不要求新增一套重复资料。作者的发布预览继续呈现完整内容，供确认前核对。

## 无登录时的发布边界

目录与已收录说明对部署地址的访问者开放。公司内网或其他网络访问范围由部署环境控制，门户不提供按用户分组的可见性。

直接发布接口使用作者 Agent 的既有 GitLab 授权，托管发布使用服务器固定群组授权，来源核验均要求有效 Maintainer/Owner 权限。新发布和更新必须带有版本 tag 与真实 GitLab Release，并在提交和确认时核验 `Release.commit.id`、`tag.commit.id` 和请求 SHA 相同，且 Release tag 与 `projectVersion` 版本一致。预览与确认需要本次短期专属凭证。**持有完整链接的人可以查看并确认本次发布**，因此不应转发；这不是实名审批，也不能声称区分了真人和自动化。MCP 不提供确认工具，发布提示词要求由作者查看并确认。历史 v1 快照保留原始字符串作者资料，按原内容读取，不自动转换或补写姓名、版本。

直接发布的 GitLab 令牌仅通过请求头提供；托管发布的原始群组授权只保存在服务器配置。每次发布记录中的临时 GitLab 授权均加密保存，用于确认时再次核验，收录完成后清除。发布记录 24 小时后失效，运行中的服务每分钟清理过期令牌，启动时也会清理；停机期间不执行清理。预览凭证与 GitLab 令牌不同；它不能读取其他候选，也不能读取任意仓库文件。目录只展示 manifest 声明的共享资料，不直接展示上传的完整源码。

## 验证口径

本地自动化使用明确标注的 GitLab 协议测试服务和 PostgreSQL 引擎，验证真实服务逻辑、持久化、网页与 MCP 进程。测试服务不会被运行配置自动启用，也不会给正式目录预置 17 项 Mock。

真实 GitLab 读权限、项目资料收录、具体 AI Host 接入和部署验收分别报告；本地通过不代替这些结果。历史交互原型在 `?prototype=1` 保留用于比对，其模拟状态不进入新目录。
